## ドッグフーディング（実施済み）

spectoru 自身のテストを spectoru でサイト化した。

- リポジトリルートに `spec-site.toml` を置いた。source は「ユニットテスト」
  （`src/`）と「契約テスト・統合テスト」（`tests/`）の 2 つ
- `cargo xtask spec-site` で `dist/` に生成する。`--strict` 付きなので、
  自分の仕様が自分の品質基準を満たさなくなった時点で落ちる
- CI に `spec-site` ジョブを追加し、生成できることと外部リソースを読み込んで
  いないことを検証する

結果は **239 spec / 警告 0**。`cargo xtask ci` が数えるテスト数と一致した。

### ドッグフーディングで見つかった設計の穴: 除外の仕組みが無い

`crates/spectoru/tests/fixtures/` にはパーサへの入力データが入っている。
これらは spectoru の仕様ではないのでサイトに載ると内容として誤りになるうえ、
意図的に構文を壊したファイルまで含まれており error になっていた。

`.gitignore` に載っていない「コミットされているが仕様ではないもの」を外す
手段が無いという穴で、フィクスチャや生成コードを持つプロジェクトなら
どこでも踏む。`[[sources]].exclude` を追加して解決した（0004 の想定にも
方向性ドキュメントにも無かった項目）。

## リリース workflow

CLAUDE.md は「ローカルからのリリースは絶対に行わない」と定めているが、
その受け皿となる GitHub Actions が存在しない。

- タグ push をトリガーにバイナリをビルドして Release に添付する
- 対象プラットフォームを決める（最低限 `x86_64-unknown-linux-gnu`。
  macOS / Windows を含めるかは需要次第）
- `permissions` は最小限にし、既存 workflow と同様に action を
  コミット SHA でピン留めする
- リリース前に `cargo xtask ci` と `cargo xtask deny` を通す
