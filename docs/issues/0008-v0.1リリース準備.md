## ドッグフーディング（実施済み）

spectoru 自身のテストを spectoru でサイト化した。

- リポジトリルートに `spec-site.toml` を置いた。source は「ユニットテスト」
  （`src/`）と「契約テスト・統合テスト」（`tests/`）の 2 つ
- `cargo xtask spec-site` で `dist/` に生成する。`--strict` 付きなので、
  自分の仕様が自分の品質基準を満たさなくなった時点で落ちる
- CI に `spec-site` ジョブを追加し、生成できることと外部リソースを読み込んで
  いないことを検証する

結果は **239 spec / 警告 0**。`cargo xtask ci` が数えるテスト数と一致した。

### ドッグフーディングで見つかった設計の穴: 除外の仕組みが無い

`crates/spectoru/tests/fixtures/` にはパーサへの入力データが入っている。
これらは spectoru の仕様ではないのでサイトに載ると内容として誤りになるうえ、
意図的に構文を壊したファイルまで含まれており error になっていた。

`.gitignore` に載っていない「コミットされているが仕様ではないもの」を外す
手段が無いという穴で、フィクスチャや生成コードを持つプロジェクトなら
どこでも踏む。`[[sources]].exclude` を追加して解決した（0004 の想定にも
方向性ドキュメントにも無かった項目）。

## リリース workflow（実施済み）

`v*.*.*` のタグ push をトリガーに、検証 → 下書き作成 → 成果物追加 → 公開の
4 ジョブで進む。`cargo xtask dist <target>` が配布用アーカイブを作る。

対象は `x86_64-unknown-linux-gnu` と `aarch64-apple-darwin` の 2 つ。CI が
Linux、ローカル開発が macOS という想定に対応する。Windows は CI での
ビルド実績が無く、初めてのビルドがリリース本番になるのを避けたいため見送った。

### 決定: 成果物のアップロードにサードパーティ製アクションを使わない

GitHub ランナーには `gh` CLI がプリインストールされているため、リリースの
作成・アップロード・公開はすべて `gh release` で完結する。ピン留めして追跡
すべき依存が増えないぶん、サプライチェーン上の面積が小さくなる。

### 決定: 下書きを経由してから公開する

先に `--draft` で作り、各プラットフォームの成果物が揃ってから公開する。
ビルドが 1 つでも失敗したときに、中途半端なリリースが利用者から見える状態に
ならないようにするため。`fail-fast: false` にしているのは、どのプラット
フォームまで通ったかが分かる方が原因を絞りやすいから。

### 決定: タグと Cargo.toml のバージョン一致を検証する

ずれたままリリースすると、配布物の `--version` が名乗る番号とタグが食い違う。
公開後には直せないので、検証ジョブの最初に落とす。

### 残っている作業

- **LICENSE ファイルが無い**。`Cargo.toml` は `MIT OR Apache-2.0` を宣言して
  いるが、リポジトリに本文が置かれていない。配布物にも同梱されない。
  Apache-2.0 は長文で、記憶から書き起こすと誤りが混入しうるため、正典を
  取得して `LICENSE-MIT` と `LICENSE-APACHE` を追加し、`cargo xtask dist` の
  アーカイブにも含める
- CI での仕様サイトのアップロードとデプロイ（Cloudflare Pages）。
  `actions/upload-artifact` をコミット SHA でピン留めする必要がある
