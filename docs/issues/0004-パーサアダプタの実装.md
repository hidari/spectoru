# [Phase 5] パーサアダプタの実装

親: [0001](./0001-v0.1リリースまでのロードマップ.md)
依存: [0002](./0002-中間表現のproject層導入とport拡充.md)

0003 とは独立しているため並行して進められる。

## 目的

`RustParser` / `TsParser` ポートに具象実装を与える。spectoru の中核価値である
「テスト名 = 仕様文」の抽出そのもの。

## Rust パーサ（`syn`）

`ItemMod` の入れ子を辿り、`#[test]` / `#[tokio::test]` が付いた `ItemFn` を
spec として収集する。

- ファイルパスが最上位グループ（`line == None`）、`mod` はサブグループ（`line == Some(..)`）
- 関数名・モジュール名は**変換せずそのまま** `name` に入れる（Unicode 識別子が
  そのまま仕様文になる）
- `#[ignore]` が付いていれば `SpecStatus::Skipped`
- テストアトリビュートの判定はパス末尾が `test` であることを見る。
  `#[test]` `#[tokio::test]` `#[async_std::test]` などを同じ規則で拾える
- `mod foo;`（本体なし）はグループを作らない。指し先は FileWalker が
  独立した最上位グループとして拾うため

### 決定: `mod tests` は階層から取り除く

`#[cfg(test)] mod tests` はユニットテストを収める慣習的な容器であって、
仕様文としての意味を持たない。そのままグループにすると全ファイルに
`tests` という無意味な階層が挟まり、`max_depth` の予算も 1 段消費する。

名前が `tests` または `test` のモジュールを取り除き、中身を親に引き上げる。
判定を `#[cfg(test)]` の有無ではなく名前で行うのは、
`#[cfg(test)] mod 有効な画像がアップロードされたとき` のように意味のある名前を
付けた場合はグループとして残すべきだから。

### 決定: パース失敗は `Err` として返す

`syn` は構文エラーで部分的な AST を返さないため、パーサとしては失敗を
正直に返すしかない。「1 ファイルの失敗で全体を止めるか、診断に記録して
続行するか」は application 層（0005）の判断とする。

## Vitest パーサ（`tree-sitter-typescript`）

`call_expression` から `describe` / `it` / `test` を検出し、第一引数の文字列
リテラルを名前として取り出す。

- `it` と `test` は同等に扱う
- `.skip` / `.todo` は `SpecStatus::Skipped`。`.only` は実行の絞り込みであって
  仕様が無効という意味ではないので状態を変えない
- `describe.skip` の中のテストは `Skipped` を引き継ぐ。実行されない以上、
  中のテストも仕様としてはスキップ状態だから
- 修飾子は位置ではなくチェーン全体を見る（`it.concurrent.skip` が拾える）
- `.each` / `.for` は v0.1 スコープ外とし `DynamicTestName` の診断を出す
- テンプレートリテラルに補間が含まれる場合（`` it(`${x} のとき`) ``）は静的に
  名前が決まらないため、IR には含めず `DiagnosticCode::DynamicTestName` を記録する。
  補間のないテンプレートリテラルは通常の文字列として扱う
- コールバックは引数の位置ではなく種類で探す。`it(name, options, fn)` の
  ようにオプション引数が挟まっても、関数式で書かれていても辿れる
- `.tsx` は TSX 文法でパースする。TypeScript 文法では JSX の山括弧が型
  アサーションと衝突して読めない

### 決定: 構文エラーでも読めた範囲を抽出する

tree-sitter はエラー耐性があり、壊れた箇所以外は正しい構文木を返す。
Rust 側と挙動が非対称になるが、これはライブラリの性質の違いに素直に
従った結果であり、読める情報を捨てる理由がない。壊れていた事実は
`DiagnosticCode::ParseError` の警告として記録する。

## テスト

fixture となるソースファイル（`tests/fixtures/` 配下）を用意し、
それをパースした結果を検証する契約テストを書く。**fixture 自体が
「spectoru がどう解釈するか」の仕様書**になるため、意図が読み取れる
最小限のケースを丁寧に並べる。

両パーサで共通に押さえるケース:

- フラットなテストファイル / ネストしたテストファイル
- 日本語のテスト名がそのまま保持される
- テストでない関数・呼び出しを拾わない
- skip 相当の指定が `SpecStatus::Skipped` になる
- 空ファイル、テストが 0 件のファイル
- 行番号が正しい（サイトからソースへ辿れる情報のため）

## 併せて対応

両パーサが共有する後処理（ファイル直下グループの組み立て、テストを含まない枝の
刈り取り、パス区切りの正規化）を `core::tree` の純関数に切り出した。同じ規則を
2 箇所に書くのを避け、規則そのものを core のユニットテストで固定できる。
