# Spectoru 方向性ドキュメント

## 概要

Rust および TypeScript (Vitest) のテストソースコードをパースし、「仕様としてのテスト」を静的Webサイトとして可視化する汎用CLIツール。特定のプロダクトに依存せず、Rust + TypeScript で構成された任意のプロジェクトで利用できることを目指す。

### 名前の由来

「Spectoru」は「spec（仕様）を取る」という日本語の掛詞であり、同時にフランス語で「スペクトラム（spectrum）」を意味する「spectre」の響きを持つ。光のスペクトルがプリズムを通じて不可視の成分を可視化するように、Spectoru はソースコード中に埋もれたテスト仕様を抽出し、見通しの良い形で可視化する。末尾の「ru」は Rust 実装であることを示す。


## 解決したい課題

テストは仕様を表現する最も信頼できる情報源だが、ソースコードを直接読まないとその全体像が見えない。テスト名と階層構造を静的サイトとして閲覧・検索可能にすることで、「今このプロジェクトは何ができるのか」をテストの一覧から素早く把握できるようにしたい。

加えて、複数のリポジトリ（バックエンド、フロントエンド、監視システムなど）にまたがるテスト仕様を一つのサイトに集約できるようにすることで、プロジェクト全体の仕様を横断的に見渡せるようにする。

## テストの書き方

spectoru はテスト名をそのまま仕様文として表示する。そのため、テスト名自体が人間にとって読みやすい仕様文であることが前提となる。Rust の識別子は Rust 1.53 から Unicode に対応しているため、日本語を含む任意の言語でテスト名を記述できる。ツール側での変換処理（snake_case → スペース区切り等）は行わず、テスト名をそのまま使う。

### Rust テストの書き方

ファイルパスが自然な最上位のグルーピングとなる。`mod` は必要に応じてサブグループとして使えるが、必須ではない。テスト関数名がそのまま仕様文になる。

ネストを使う場合（統合テストなど、条件分岐が複数あるケース）：

```rust
// tests/integration/artwork_creation.rs

mod 有効な画像がアップロードされたとき {
    #[tokio::test]
    async fn 作品が公開状態で作成される() { /* ... */ }

    #[tokio::test]
    async fn コラボレーターにクレジットが付与される() { /* ... */ }
}

mod タイトルが未入力のとき {
    #[tokio::test]
    async fn バリデーションエラーが返される() { /* ... */ }
}
```

フラットに書く場合（E2Eテストなど、シンプルなユーザーストーリー）：

```rust
// tests/e2e/creator_registration.rs

#[tokio::test]
async fn 招待リンクからクリエイター登録が完了する() { /* ... */ }

#[tokio::test]
async fn 無効な招待コードでは登録できない() { /* ... */ }
```

テストの判定は「アトリビュートのパスの最終セグメントが `test` であること」で行う。
`#[test]` `#[tokio::test]` `#[async_std::test]` `#[test_log::test]` などが同じ規則で
拾える。テストランタイムごとに完全パスを列挙する方式だと、新しいランタイムが出る
たびに spectoru 側の更新が必要になってしまう。

`#[ignore]` が付いたテストは `skipped` として記録する。仕様文としては存在している
ため spec 数には数え、サイト上で区別して表示する。

`mod tests` と `mod test` は階層から取り除き、中身を親に引き上げる。ユニット
テストを収めるための慣習的な容器であって、仕様文としての意味を持たないため。
`mod 有効な画像がアップロードされたとき` のように意味のある名前を付けた場合は
そのままグループになる。

`mod foo;` のように本体を持たない宣言はグループを作らない。指し先のファイルは
ファイル探索が独立した最上位グループとして拾うため、二重に現れることはない。

テストを 1 つも含まないモジュールはグループにしない。`src/` 配下を対象に含めると
テストと無関係なモジュールが大量に存在するため、機械的にグループ化すると仕様
サイトが意味のない枝で埋まってしまう。

### Vitest テストの書き方

Rust 側と同様、`describe` によるネストは任意。`it` / `test` の文字列がそのまま仕様文となる。

ネストを使う場合：

```typescript
// app/tests/artwork-creation.test.ts

describe("有効な画像がアップロードされたとき", () => {
  it("作品が公開状態で作成される", () => { /* ... */ });
  it("コラボレーターにクレジットが付与される", () => { /* ... */ });
});

describe("タイトルが未入力のとき", () => {
  it("バリデーションエラーが返される", () => { /* ... */ });
});
```

フラットに書く場合：

```typescript
// app/tests/e2e/creator-registration.test.ts

it("招待リンクからクリエイター登録が完了する", () => { /* ... */ });
it("無効な招待コードでは登録できない", () => { /* ... */ });
```

`it()` と `test()` は同等に扱う。

修飾子つきの呼び出しは次のように解釈する。

| 記法 | 解釈 |
|---|---|
| `it.skip` / `it.todo` / `describe.skip` | `skipped`。`describe.skip` の中のテストも `skipped` を引き継ぐ |
| `it.only` | 通常の spec。どれを走らせるかの指定であって、仕様が無効という意味ではない |
| `it.concurrent` など上記以外 | 通常の spec |
| `it.each` / `it.for` | v0.1 では対象外。名前が実行時にしか決まらないため diagnostics に記録する |

テスト名は文字列リテラルか、補間を含まないテンプレートリテラルである必要がある。
変数や補間つきテンプレートリテラル（`` it(`${条件}のとき`) ``）は静的に名前が
決まらないため IR には含めず、警告として記録する。

`describe` のコールバックは引数の位置ではなく種類で探すため、
`it("名前", { timeout: 1000 }, () => {})` のようにオプション引数が挟まっても、
関数式で書かれていても認識できる。

`.tsx` ファイルは TSX 文法でパースする。TypeScript 文法では JSX の山括弧が
型アサーションと衝突して読めないため。

Rust 側と同様、テストを 1 つも含まない `describe` はグループにしない。

### ツールが出す警告

spectoru は書き方の自由度を尊重しつつ、仕様としての可読性が損なわれる場合に警告を出す。

- ネストの深さがデフォルト上限（4階層）を超えている場合。テストの条件分岐が深すぎるということは、テスト対象の実装自体が複雑すぎる可能性を示唆するシグナルでもある。上限値は設定ファイルで変更可能。
- テスト名が空文字の場合。

厳格モード（`--strict`）を用意し、警告が1つでもある場合に exit code 1 で終了するようにする。CIでの品質ゲートとして利用できる。

## 中間表現

### なぜ JSON か

中間表現には2つの役割がある。1つは extract と render を疎結合にするための内部境界。もう1つは、複数リポジトリを集約するパターンにおいて、ファイルとして永続化・転送されるアーティファクトとしての役割。

前者だけであれば Rust の型定義が本体であり、シリアライゼーションフォーマットは serde が吸収する実装詳細に過ぎない。しかし後者の役割を考えると、GCS や GitHub Artifacts に置かれたフラグメントファイルを人間がデバッグ目的で開いて読む場面が想定される。この観点から、人間可読性と汎用性を兼ね備えた JSON を採用する。

今回の中間表現はグループのツリーと末端のスペックという単純な構造であり、JSON で過不足なく表現できる。TOML は深いツリーの表現に不向き、YAML は暗黙の型変換の落とし穴が多く Rust エコシステムでの安定性にも懸念がある、バイナリフォーマット（MessagePack 等）は人間可読性を失うという理由で不採用とした。

### 構造

中間表現は `project → source → group → spec` の4階層で構成される。

- **project**: 1 つの `spec-site.toml`（= 1 つの作業ディレクトリ、= 1 つの git リポジトリ）に対応する。JSON フラグメント 1 ファイルが 1 project。
- **source**: 設定の `[[sources]]` 1 件に対応する。モノレポで Rust バックエンドと Vitest フロントエンドが同居する場合、1 project に 2 source がぶら下がる。
- **group / spec**: 自由なツリー構造。固定のロール分類（Subject / Context / Expectation 等）は行わない。ファイルパスが暗黙の最上位グループとなり、その中に `mod`（Rust）や `describe`（Vitest）によるサブグループが任意の深さで存在しうる。

`repository` / `revision` / `extracted_at` が source ではなく project に載るのは、1 つの設定ファイルが指すのは常に単一の作業ディレクトリであり、その中の全 source が同じリビジョンを共有するため。source 側に複製すると同じ事実が複数箇所に現れて同期ズレの余地が生まれる。

同じ理由で、`stats` も project に 1 つだけ持つ。source ごとの内訳が必要な場合はレンダラが `sources` ツリーから都度算出する。

source に言語種別を持たせないのも同様の判断による。言語は spec ごとの `language` が事実として保持しており、設定上の `kind` を IR に複製すると両者が食い違いうる。

```jsonc
{
  "project": {
    "name": "Astralys",
    "repository": "https://github.com/HermitianHQ/astralys",  // optional
    "revision": "abc1234",   // git SHA, optional
    "extracted_at": "2026-04-13T12:00:00Z"
  },

  "sources": [
    {
      "name": "Backend",
      "groups": [
        {
          // ファイルパスが最上位グループ
          "name": "tests/integration/artwork_creation.rs",
          "file": "tests/integration/artwork_creation.rs",
          "children": [
            {
              "name": "有効な画像がアップロードされたとき",
              "file": "tests/integration/artwork_creation.rs",
              "line": 3,
              "children": [],
              "specs": [
                {
                  "name": "作品が公開状態で作成される",
                  "file": "tests/integration/artwork_creation.rs",
                  "line": 5,
                  "language": "rust",
                  "status": "active"
                },
                {
                  "name": "コラボレーターにクレジットが付与される",
                  "file": "tests/integration/artwork_creation.rs",
                  "line": 9,
                  "language": "rust",
                  "status": "active"
                }
              ]
            }
          ],
          "specs": []
        },
        {
          // フラットなテストファイル：グループ直下に spec が並ぶ
          "name": "tests/e2e/creator_registration.rs",
          "file": "tests/e2e/creator_registration.rs",
          "children": [],
          "specs": [
            {
              "name": "招待リンクからクリエイター登録が完了する",
              "file": "tests/e2e/creator_registration.rs",
              "line": 3,
              "language": "rust",
              "status": "active"
            },
            {
              "name": "無効な招待コードでは登録できない",
              "file": "tests/e2e/creator_registration.rs",
              "line": 7,
              "language": "rust",
              "status": "skipped"
            }
          ]
        }
      ]
    }
  ],

  "diagnostics": [
    {
      "level": "warning",
      "code": "nesting_too_deep",
      "message": "Nesting depth exceeds limit (5 > 4)",
      "file": "tests/integration/complex_flow.rs",
      "line": 30
    }
  ],

  "stats": {
    "total_specs": 42,
    "warnings": 1,
    "languages": {
      "rust": 30,
      "typescript": 12
    }
  }
}
```

`status` は `active` / `skipped` の2値で、Rust の `#[ignore]` と Vitest の `.skip` に対応する。スキップされていても仕様文としては存在しているため `total_specs` には含める。

`diagnostics[].code` は機械可読な分類コード。メッセージ文言の変更が CI の判定を壊さないよう、`--strict` 以外の細かい制御はこのコードを使う。

### 抽出の決定性

`extracted_at` は実行時刻という副作用そのものであり、素朴に実装すると extract の出力が実行のたびに変わってテストが決定的でなくなる。時刻取得は Clock ポートに切り出し、テストでは固定値を返す実装を注入して IR 全体を比較できるようにする。同じ理由でファイル探索の結果もパス順にソートし、入力が同じなら必ず同じフラグメントが出るようにする。

ファイル探索では、リポジトリ内の `.gitignore` と `.git/info/exclude` は尊重するが、利用者ごとのグローバル gitignore（`~/.config/git/ignore`）は読まない。同じソースツリーからでも実行環境によって抽出結果が変わってしまうため。`target/` と `node_modules/` は `.gitignore` に載っていなくても常に除外する。

## CLI インターフェース

### サブコマンド

```bash
# ソースをパースし、静的サイトを一発生成（extract + render）
spectoru build --config spec-site.toml --out dist/

# extract のみ（JSON フラグメント出力）
spectoru extract --config spec-site.toml --out spec-fragment.json

# 複数フラグメントからサイト生成
spectoru render --fragments backend.json frontend.json monitoring.json --out dist/

# 規約チェックのみ（CI 品質ゲート向け）
spectoru lint --config spec-site.toml --strict
```

`build` は単一リポジトリで完結する最もシンプルなケース向け。複数リポジトリ集約時は各リポジトリで `extract` を実行し、spec-site リポジトリで `render` する。

### 設定ファイル（spec-site.toml）

```toml
[project]
name = "Astralys"
repository = "https://github.com/HermitianHQ/astralys"  # optional

[[sources]]
name = "Backend"
kind = "rust"
paths = ["src/", "tests/"]

[[sources]]
name = "Frontend"
kind = "vitest"
paths = ["app/"]

[lint]
max_depth = 4  # ネスト深さの上限（デフォルト: 4）
```

`repository` は project セクションに置く。1 つの設定ファイルが指すのは単一の作業ディレクトリであり、その中の全 source は同じリポジトリに属するため。`revision` は設定には書かず、extract 時に git から解決する。

## レンダリング

### 出力形式

単一 HTML + インライン CSS / JS で構成される、**外部依存ゼロ**の静的サイト。CDN を含め外部ホストへのリクエストは一切行わない。

当初は検索ライブラリ（minisearch）を CDN から読み込む想定だったが、これは採用しない。SRI なしの外部スクリプト読み込みは、CDN または配信元パッケージが侵害された時点でサイト閲覧者のブラウザ上で任意コード実行を許す経路になる。spectoru が出力するのは組織の内部仕様を並べたサイトであり、閲覧者は開発者である。サプライチェーンの影響範囲をアダプター層に閉じるという方針とも矛盾する。

検索は自前実装で足りる。対象はテスト名の文字列だけで、規模も数千 spec のオーダー。正規化したトークンの前方一致・部分一致インデックスをビルド時に生成して HTML にインライン化すれば、ライブラリを持ち込む理由がない。

出力 HTML はテスト名をそのまま表示するが、テスト名は任意の文字列（`<script>` を含みうる）であるため、**埋め込み時のエスケープは必須**。これは契約テストで固定する。

### サイト構造

- サイドバー: プロジェクト → ソース → ファイル → グループの階層ツリー
- メインエリア: 選択されたグループのサブグループとスペックをネスト表示
- 検索バー: テスト名での全文検索（インクリメンタルサーチ）
- 統計ヘッダー: 全体の spec 数、言語別内訳、警告数

### 複数プロジェクト集約時

`render` サブコマンドに複数の JSON フラグメントを渡した場合、サイドバーの最上位にプロジェクト名が並ぶ。一つのサイトで横断的に検索可能。

## パース処理

### Rust テスト（syn ベース）

`syn` クレートでソースファイルをパースし、`ItemMod` の入れ子構造と `ItemFn` の `#[test]` / `#[tokio::test]` アトリビュートを辿る。テスト関数名とモジュール名はそのまま中間表現の `name` フィールドに格納する（Unicode 識別子がそのまま使われるため変換不要）。

### Vitest テスト（tree-sitter-typescript ベース）

`tree-sitter-typescript` の Rust bindings を使用する。`call_expression` ノードから `describe` / `it` / `test` の呼び出しを検出し、第一引数の文字列リテラルをテスト名として抽出する。tree-sitter は Rust 実装であるため bindings のオーバーヘッドは最小限。

### 構文エラーの扱いが言語間で異なる理由

Rust 側は構文エラーでパース自体を失敗させ、Vitest 側は警告を出しつつ読めた範囲を
抽出する。これはライブラリの性質の違いによる。`syn` は全体が読めなければ AST を
返さないのに対し、tree-sitter はエラー耐性を持ち、壊れた箇所以外は正しい構文木を
返す。読める情報を捨てる理由はないため、それぞれの性質に素直に従う。

なお「1 ファイルのパース失敗で処理全体を止めるかどうか」はパーサではなく
application 層の判断であり、パーサは失敗を正直に返すだけにとどめる。

## CI 統合パターン

### パターン A: 単一リポジトリ

```yaml
on:
  push:
    branches: [main]

jobs:
  spec-site:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install spectoru
        run: cargo install --git https://github.com/HermitianHQ/spectoru
      - name: Build spec site
        run: spectoru build --config spec-site.toml --out dist/
      - name: Deploy to Cloudflare Pages
        uses: cloudflare/pages-action@v1
        with:
          directory: dist/
```

### パターン B: 複数リポジトリ集約

各リポジトリの CI で `extract` を実行し、JSON フラグメントをストレージにアップロードする。spec-site リポジトリの CI が全フラグメントを集めて `render` する。

各リポジトリ側：

```yaml
- name: Extract specs
  run: spectoru extract --config spec-site.toml --out spec-fragment.json
- name: Upload to GCS
  run: gsutil cp spec-fragment.json gs://spec-fragments/${{ github.repository }}/latest.json
```

spec-site リポジトリ側：

```yaml
- name: Download all fragments
  run: gsutil -m cp "gs://spec-fragments/*/latest.json" fragments/
- name: Render site
  run: spectoru render --fragments fragments/*.json --out dist/
- name: Deploy
  uses: cloudflare/pages-action@v1
  with:
    directory: dist/
```

## 初期スコープと除外事項

### v0.1 で含めるもの

- Rust テストの抽出（syn ベース。`#[test]`, `#[tokio::test]`, mod 階層）
- Vitest テストの抽出（tree-sitter-typescript ベース。`describe`, `it`, `test`）
- ネスト深さの検証と diagnostics 出力
- JSON 中間表現の出力（extract サブコマンド）
- 単一 HTML 静的サイトの生成（build / render サブコマンド）
- クライアントサイド全文検索

### 将来的に検討するが v0.1 では含めないもの

- テスト実行結果（pass/fail）の反映: テスト実行を伴うため extractor の責務を超える。JUnit XML 等のレポートを別途読み込む拡張として将来対応の可能性あり。
- Extractor プラグイン機構: 新しい言語対応を外部プラグインとして追加する仕組み。最初はハードコードで十分。
- テーマ・デザインカスタマイズ: デフォルトテーマ一択でシンプルに始める。
- crates.io への公開: 安定するまでは `cargo install --git` で配布。
- watch モード: ローカル開発でのファイル監視 → 自動リビルド。
